# Jump 卡牌售卖分析 Case

用于复盘**新角色首发、老角色返还、限定卡池**的收入表现。目标不是只回答“卖得好不好”，而是将收入差异拆到可验证的行为链路：

`活跃规模 → 付费转化 → 付费深度 → 卡池参与/抽数 → 胚子来源与养成 → 券与商品路径`

## 先回答的四个问题

1. 首周（或首日）收入差异主要来自活跃用户规模、付费率，还是 ARPPU？
2. 用户是否真正进入目标卡池，并走到 `1–39 / 40–79 / 80+` 的哪一档？收入少在何档？
3. 老角色返还是否抑制付费，还是返还用户仍为觉醒/养成继续投入？
4. 限时刊物券、跃之星、意志结晶等资源，是通过存量、商城、兑换还是活动奖励支持了抽卡？商品 SKU 是否改变了付费结构？

不要将“返还用户 ARPU 低”直接写成“返还导致收入下降”。这是观察性分析；只有在同口径、同生命周期、控制历史价值与资源存量后，才能讨论返还的增量影响。

## 推荐流程

### 0. 建立角色事件表

编辑 [`config/card_pool_events.example.csv`](config/card_pool_events.example.csv)。每个角色一行，明确：

- `launch_date`：角色/卡池实际开始日；若中午开池，首日建议使用精确时间窗，不能把当天 0 点到开池前的充值算入角色收入。
- `end_date`：首周通常为 `launch_date + 6 天`。
- `hero_id`、`gacha_id`：必须经埋点核对。
- `is_return_pool` 与 `return_reason`：返还仅由 `hero_add` 的真实返还原因识别，不能用“已拥有角色”代替。

### 1. 先做全量收入拆分

以活动期活跃用户为分母，计算：

$$收入 = 活跃用户数 × 付费率 × ARPPU$$

同时看 ARPU：

$$ARPU = 收入 / 活跃用户数，\qquad ARPPU = 收入 / 付费用户数$$

收入规模变化建议用对数均值分解或顺序替换，避免把“用户少”误判为“角色吸引力弱”。基础结果来自 `01_user_panel.sql`，可由 `scripts/summarize_panel.py` 汇总。

### 2. 看目标卡池参与深度，而不是只看持有

将每位用户在目标 `gacha_id` 的实际抽数分为：`0`、`1–39`、`40–79`、`80+`。

- `0`：没有进入卡池；不应被“持有角色”替代，因为可能来自返还。
- `1–39`：尝试或用存量抽卡；未达到 40 抽保底。
- `40–79`：到达至少一个保底，适合观察胚子获取与继续养成意愿。
- `80+`：深抽用户，通常是 ARPPU 的主要来源。

每个档位均输出：用户数、收入、付费人数、付费率、ARPU、ARPPU、平均抽数、胚子来源、等级与觉醒。比较两个卡池时必须同时比较**人数**和**单人收入**；例如 80+ 档收入增加，可能是深抽人数更多，也可能是同一人数花得更多。

### 3. 单独判断返还机制

将老角色池活跃用户拆为：

- `返还用户`：活动期 `hero_add`，目标 `hero_id`，且 reason = `角色返回模块`（以项目真实枚举为准）。
- `非返还用户`：其余活动用户；其中可继续单列“目标角色抽卡获得者”。

返还相当于给予一个胚子，机制上约减少 **40 抽**的首胚子门槛；但最多 3 觉时，仍可能需要额外胚子。因此需要同时看：返还用户的抽数、40+/80+占比、觉醒、等级、ARPU/ARPPU，而不是只看“是否免费获得”。

若要估计返还的因果影响，优先采用“历史期活跃且价值相近”的匹配对照：在返还前的活跃天数、历史付费、历史抽卡、段位、期初资源、角色持有数相近的**非返还用户**中匹配。对照组不是所有非返还用户。

### 4. 解释 ARPPU 的变化

按支付金额段（例如 `$0–10 / $10–50 / $50–100 / $100–500 / $500+`）拆解：

- 每档付费人数占比；
- 每档收入占比；
- 高额付费人数是否减少；
- 相同抽数档中 ARPPU 是否下降。

再用 [`02_product_revenue.sql`](sql/02_product_revenue.sql) 查看所有 SKU（不只 Top 5），重点关注限时阅览券礼包、战令、直购礼包。判断“小额付费率提高”时，必须区分：是新增小额付费人数，还是高额付费用户降档。

### 5. 资源与券路径：看数量、时间点、来源

资源分析至少包含：

- **期初存量**：活动开始前最近一次快照；不是活动日凌晨之后的快照。对中午开池必须使用开池前的最后快照。
- **活动期正向产出**：商城购买、道具兑换、玩家充值、活动奖励、邮件/GM/未知来源。
- **活动期消耗**：跃之星、意志结晶、指定兑换道具，以及目标卡池抽数。

“有存量”没有解释力；必须输出中位数、均值、分位数与分桶（例如 0、1–39、40–79、80+ 等价抽数）。返还胚子也应作为“等价 40 抽”的单独字段，不要混入真实抽数。

若发现 80+ 用户“付费更少但养成相近”，不能直接断言存在免费券。先核查：

1. 资源快照字段是否反了（如免费/付费跃之星）；
2. 是否排除了内部、水量、异常 IP 与福利号；
3. `resource_change` 是否存在邮件/GM/运营活动等大量产出；
4. 商城是否可通过活动道具兑换券；
5. 商品 SKU 的券数量、价格、限购是否变更。

### 6. 用养成和对局验证“抽卡行为是否真实有效”

比较相同抽数档的不同角色：等级、天赋/装备、觉醒数、Day7 三觉率、排位出场率、胜率和 MVP 率。若养成相近而付费显著较低，才是“更低成本资源路径”值得深挖的信号；若养成也低，则更可能是用户并未继续养成。

## 固定口径

| 指标 | 定义 | 常见误用 |
|---|---|---|
| 活跃用户 | 活动窗口内至少一次 `LOGIN_SUCCESS`，排除黑名单 | 用目标角色持有者做分母 |
| 收入 | 有效 `PURCHASE`，扣 wallet freeamount，按当日汇率换算 USD，排除沙盒 | 将开池前当天收入算给新卡 |
| 付费率 | 付费用户 / 活跃用户 | 以持有者为分母但称“整体付费率” |
| ARPU | 收入 / 活跃用户 | 把 ARPU 当作付费深度 |
| ARPPU | 收入 / 付费用户 | 忽略付费用户构成变化 |
| 卡池参与率 | 目标池抽数 > 0 的用户 / 活跃用户 | 用“获得角色人数”替代 |
| 返还用户 | 指定 hero_add 返还原因的用户 | 所有已持有老角色的用户 |
| 期初存量 | 开池前最近快照 | 活动开始后快照 |

黑名单最少包括 `internal_users`、`is_water`、`is_water_mod`、`suspicious_ip`。此外，本项目历史上出现过单笔发放 5,000 / 10,000 / 20,000 / 30,000 资源的福利号；应额外保留 `possible_welfare_account` 标记，既可排除，也可做敏感性复核。

## 文件说明与执行顺序

1. 编辑 `config/card_pool_events.example.csv`，并将其中的 `event_def` 粘贴到 SQL。
2. 使用 [`scripts/export_queries.ps1`](scripts/export_queries.ps1) 将模板复制到 `fivecross-data-client/tasks/adhoc`。
3. 执行 [`sql/01_user_panel.sql`](sql/01_user_panel.sql) 获取用户粒度底表。
4. 执行 [`scripts/summarize_panel.py`](scripts/summarize_panel.py) 生成指标、抽数档、返还组、券来源汇总。
5. 执行 [`sql/02_product_revenue.sql`](sql/02_product_revenue.sql) 与 [`sql/03_ticket_resource_ledger.sql`](sql/03_ticket_resource_ledger.sql) 解释商品与资源路径。
6. 用 `04_validation_checklist.md` 完成口径检查，再写报告或 PPT。

SQL 中的中文 `reason` 值和 `resource id` 必须以实际埋点枚举为准；模板内的值是本次 Jump TW 分析已验证的默认值。

## 首五日衰减复盘（西索 vs 波风湊）

当问题是“波风湊首日高、后续下滑快；西索首日低、下滑平滑”时，不能只按每日 DAU 比较，因为 Day5 活跃用户已经换了一批。按以下顺序复核：

1. `04_hisoka_minato_first5d_user_daily.sql`：全体日活口径，观察每日收入、ARPU、ARPPU、抽数和返还状态。
2. `06_hisoka_minato_day1_cohort.sql`：固定 Day1 活跃用户 cohort，拆出 Day2–5 的留存、复购、抽数与角色等级/觉醒，判断衰减是否只是用户流失。
3. `07_hisoka_minato_first5d_product_daily.sql`：按日查看全部 SKU，定位高额包的购买人数及收入何时减少。
4. `scripts/analyze_day1_transitions.py`：按 Day1 付费档观察 Day2–5 复购、后续抽数与 Day5 养成。

若业务方指出“同期神秘商店”等干扰项，不要只依据运营配置名称删除数据。先以 `active_shop` 的**实际 shop_id、goods_id、时间和资源流水**验证；再将命中用户作为暴露组，输出其目标池抽数与非暴露用户的对照。活动映射未验证前，只能称为“候选干扰项”。
