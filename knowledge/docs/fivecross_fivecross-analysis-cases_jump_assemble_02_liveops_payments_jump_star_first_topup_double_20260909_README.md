# JUMP Assemble TC｜躍之星各檔首儲雙倍成效評估（2026-09-09 起）

## 決策問題

2026-09-09 上線「每位玩家、每個躍之星儲值檔位，活動後首次購買可獲得 2 倍躍之星」，且機制長期持續。本 case 用於回答：

1. 覆蓋了多少活躍玩家、多少人實際參與，各檔位的參與人數與滲透率如何？
2. 參與者原本是哪一類付費玩家；活動是否帶來破冰、喚回、提檔與多檔連買？
3. 各檔位尚未使用首儲雙倍機會的「活躍存量」如何變化，後續可轉化空間還有多大？
4. 活動同期的付費率、收入、ARPU、ARPPU、訂單與檔位結構是否改善；是否可能只是提前儲值或檔位替代？
5. 雙倍發放的躍之星是否被消耗、沉澱或擠壓後續儲值，單位增量收入換來多少額外貨幣投放？

主要使用者是營運、商業化與產品團隊。分析應支持「是否繼續原機制、針對哪些存量做提醒、是否調整檔位與獎勵、是否需要補埋點」的決策。

## 核心定義

- **有效購買**：`PURCHASE`、非 `SANDBOX_RECEIPT`、玩家 ID 非空，並排除 `internal_users`、`is_water`、`is_water_mod`、`suspicious_ip`。收入需扣除 wallet `freeamount` 並按當日匯率換算 USD。
- **活躍玩家**：當日有 `LOGIN_SUCCESS` 的去重 account。所有「活躍存量」指標都只在此集合內計算。
- **活動參與者（購買代理）**：9/9 起首次購買某個合資格檔位的玩家；同一玩家可在多個檔位參與，但整體參與人數必須去重。
- **已核實領獎者**：購買代理之外，能在資源流水中核對到該檔首次雙倍贈送者。若沒有專用 `campaign_id/reason/sub_reason`，不可把「買過合資格 SKU」表述成已確認拿到雙倍。
- **檔位機會存量**：某日活躍且截至該日前仍未在活動期買過該檔位的人。每位玩家在 8 個檔位各有一個機會，因此各檔存量可比較，但不可跨檔相加為人數。
- **破冰**：9/9 前從 OBT 起沒有任何有效付費，9/9 後第一筆有效付費是合資格躍之星檔位。
- **喚回付費**：9/9 前有付費，但距活動後首筆合資格檔位購買已超過 30 天。
- **提檔**：9/9 前買過的躍之星檔位最高售價低於 9/9 後首次買到的更高檔位。另輸出嚴格口徑「活動前只買低檔（<= NT$290），活動後買高檔（>= NT$430）」。
- **充滿**：9/9 起已購買全部 8 個合資格檔位各至少一次。另輸出 `1/2/3/4/5/6/7/8` 檔完成深度，避免只看極少數全滿玩家。
- **完成率分母**：活動期至少一天活躍的去重玩家；參與深度分布另以活動參與者為分母。兩種分母不可混用。

## 建議 KPI 層級

### 1. 主要成效 KPI

1. 活躍玩家參與率：活動參與者 / 活動期活躍玩家。
2. 破冰率：破冰人數 / 活動期活躍且活動前未付費玩家。
3. 每活躍玩家增量收入：活動後實際 ARPU 相對同星期基準的差額；沒有實驗對照時只稱「同期差額」，不稱因果增量。

### 2. 驅動指標

- 各檔位每日/累計參與人數、機會使用率、剩餘活躍存量。
- 參與者活動前付費身分、歷史最高檔、歷史累積付費、距上次付費天數。
- 破冰、喚回、同檔、提檔、降檔人數與檔位轉移矩陣。
- 每人完成檔數、多檔連買、充滿、到第 N 檔/充滿所需天數。
- 首次參與後 D1/D3/D7 活躍、D7/D14 再付費與非雙倍商品付費。

### 3. 護欄

- ARPPU、後續非獎勵訂單、活動後第 2 次同檔購買率，防止只把需求前置。
- 獎勵躍之星發放量、7/14 日消耗率、期末餘額，評估經濟投放成本。
- 收入集中度（Top 1%/5%）、退款/重複單/缺匯率/未知 SKU，防止少數大戶或資料問題誤導。

## 必看的切分角度

- 檔位：單檔、低（33–290）、中（430–630）、高（1470–2990）。
- 玩家：未付費、新付費、沉默付費、近期付費；歷史最高檔與歷史累積付費分層。
- 行為：單檔、多檔、由低到高、由高到低、一天內連買、跨日完成。
- 來源：平台、幣別、註冊 cohort、活動前活躍頻次；有渠道欄位時再補渠道。
- 時間：D1/D3/D5/D7、自然週、活動前四週同星期、成熟 cohort。

## 解讀順序

1. 先做資料核對：8 檔 SKU 是否齊、訂單是否可去重、雙倍發放是否能直接辨識。
2. 看觸達與漏斗：活躍基數 → 至少參與一檔 → 多檔 → 高檔 → 充滿。
3. 看人群增量意義：破冰與喚回優先於既有大戶；提檔需同時看之後是否降檔/停止付費。
4. 看收入與經濟成本：收入提升若伴隨 ARPPU 下滑可能是低門檻擴面；若只在前幾日尖峰且後續回落，可能是需求前置。
5. 最後才談歸因：沒有隨機對照，9/9 同期還有角色/卡池與其他活動，前後差異只能描述為同期關聯。可用同星期基準、玩家固定效應或未使用機會的相近玩家做穩健性比較，但仍非嚴格因果。

## 復跑方式

1. 先執行 `00`，按查詢結果修正每個 SQL 的 `tier_map`；確認是否存在可直接識別首儲贈送的欄位/事件。
2. 各 SQL 預設 `analysis_end = CURRENT_DATE - 1 day`，避免當日未完結；需要固定快照時將其改成明確日期。
3. 依序執行 `01`–`07`，保存原始結果時在檔名加上截止日，例如 `02_participation_20260913.csv`。
4. 每週更新 `01/03/05/06`；破冰、提檔和充滿均為累積型指標，報告時同時展示新增量與累計量。

## 已知限制與待確認

- 目前只有畫面與既有事件表，尚未確認 8 個正式 productid、各商店平台的別名，以及雙倍資源的專用埋點。`PURCHASE` 只能作為參與代理。
- 若 9/9 是既有玩家也重置一次機會，本文口徑成立；若機會其實依帳號生命週期首次購買、且歷史已購者不重置，需將 eligibility 改為「全歷史未買過該檔」。
- 若退款/撤銷不會回寫 `PURCHASE`，需接支付訂單真相表扣除退款；目前 SQL 僅排除 sandbox。
- OBT 歷史起點暫按 `2026-06-24`。因此「從未付費」精確含義是「自此日期起未觀測到付費」。
- 活躍存量會受 DAU 組成波動影響；解讀時同時看絕對人數與占當日 DAU 比例。
