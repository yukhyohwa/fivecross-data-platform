# 工具结果通道预算（字符上限与行溢出）

## chat_bi 实际标定（以此为准，下方 JoyTools 数字仅作溯源参考）
- chat_bi 已吸收 spill/信封机制，但标定参数不同：兜底字符上限 = settings.AGENT_TOOL_RESULT_MAX_CHARS（默认 4000，不是 45,000）；样本行按预算浓缩（不是固定 5 行）；完整结果入 session_store.ResultStore（会话内保留最近 8 份，不是 24 小时产物库）。
- 信封字段名也不同：result_id / columns / rows / sample_rows / total_rows / truncated / readback，读回用 read_result_rows（每页最多 500 行）。
- 纪律不变：样本不是数据、截断如实说明、选列取全、能读回不重查。

## 三道闸（JoyTools 原实现，溯源参考）
- 上面有两道**硬闸**都不是我们的：Claude Code 的工具结果层 50,000 字符、MCP 层约 25k tokens。撞上任何一道，JSON 会被截成非法片段——页面 json.loads 失败后把整个结果丢掉，模型据以作答的数据同样残缺。
- 我们自己的兜底线：TOOL_RESULT_MAX_CHARS = 45,000，在信封层（services/tool_catalog.py::execute_tool）统一执行。它是通道的属性，不是某个能力的属性。

## 行溢出才是常规手段（spill）
- ROW_PAYLOAD_BUDGET_CHARS = 30,000，实测标定：OBT 179 天 6 列 21,425 字符、7 列 25,339，全宽 27 列 94,307 溢出。
- 超预算时：完整行落盘产物库（24 小时清理），信封只回 5 行样本（SAMPLE_ROWS=5）+ rows_artifact 引用 + caveats 提示「完整数据已在页面上渲染成表格」。
- 样本只用于认列名和取值形态，**不是分析数据**——不要据样本下结论，也不要靠拉大 limit 硬取全量。
- 页面侧用 load_spilled_rows 读回；本对话的 rows_artifact 可用 read_result_rows 按页读回，能读回不重查。

## 兜底线接非 rows 字段
45,000 不该经常被撞到：它专门接住非 rows 字段独自把信封撑爆的情况——实测 kpi_overview(group_by=["country_code"], include_summary=True, summary_limit=200) 的 summary 一项就 56,805 字符，rows 早已溢出，信封仍有 61,452 字符。

## 注意事项
- 截断如实说明：next_offset 非空即还有后续页，不得声称"全部"。
- 选列取全：分析时用 columns 只取需要的列，全宽结果很快就会超出通道、只能拿到几行样本。
