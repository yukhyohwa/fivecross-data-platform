# JUMP 排位赛匹配平衡分析

这是一套可重复执行的 JUMP 匹配体验分析 case。核心目标是把“单排撞车组队、双方段位差、Bot 投放差异、星耀 21+ 规则、匹配等待时间、双排英雄杯差”放在同一套数据口径和 QA 流程下，避免每次临时拼 SQL。

## 先看结论口径

- 主分析范围是 `ta.v_event_23` 的排位赛：`model_type = 2`。
- 真人局指同一 `battle_id` 的 `arena_fight` 记录中 `MAX(robot_num)=0`。
- 单/双/三排来自匹配开始事件 `battle_process AND log_type=4` 的 `team_member_num=1/2/3`。
- 匹配开始事件通常没有 `battle_id`，所以按同一 `lcx_id` 关联结算前最近一次匹配开始，窗口不超过 30 分钟。历史校验覆盖率 100%，中位间隔 343 秒，P99 为 771 秒。
- 暂用结算 `rank` 作为双方阵营代理键。只有恰好两个 `rank` 的对局才能进入依赖双方阵营的分析；如果以后有正式 `camp_id/team_id`，必须替换。
- `player_ladder_level` 数值越大代表段位越高；段位名称按 `RankLevel.xlsx` 映射。
- 默认排除 `user_result_cluster_23` 中 `internal_users`、`is_water`。
- `hero_trophy` 是数组字段，英雄杯使用 `TRY_CAST(hero_trophy[1] AS DOUBLE)`。
- 所有结论都是观察性证据。Bot 集中只能生成复核名单，不能单凭这些数据认定刷分或作弊；`score` 也不是排位积分。

## 指标定义

### 单排撞车组队

分析单位是一名单排真人玩家的一场对局。对方阵营最大 `team_member_num`：

- 1：对方纯单排；
- 2：对方含双排；
- 3：对方三排。

三类必须互斥且占比合计 100%。胜利暂以本方 `rank=1` 判断。

### 严格段位不均衡

当强方最低段位仍高于弱方最高段位，即：

```text
MIN(强方 ladder_level) > MAX(弱方 ladder_level)
```

该定义直接对应“对方全员都高于己方”，不会把平均值较高但仍有交叉的对局算入。

### Raw Bot 率与标准化 Bot 率

- Raw Bot 率：某排队类型的 Bot 玩家-对局记录数 / 该类型全部玩家-对局记录数。
- 标准化 Bot 率：先在“日期 × 段位带”内算各排队类型 Bot 率，再用共同样本结构加权。它减少双排玩家所在日期、段位构成不同带来的混杂。

两者回答不同问题，应并列展示。另一个“全局去重 battle Bot 率”以对局为分母，不能与玩家暴露 Bot 率直接比较。

### 双排英雄杯

每个含两名 `queue_size=2` 玩家的一方形成一个“双排阵营视角”。双排均值只取这两名双排玩家；对手均值取对方所有已观察真人。双排对双排时一局会形成两个阵营视角，这是预期行为。

## 执行

1. 复制 `config/analysis.example.json` 为 `config/analysis.json`，设置日期和 `fivecross-data-client` 路径。
2. 确认数数登录有效；必要时在客户端目录执行 `venv/Scripts/python.exe main.py --login --region global`。
3. 在本 case 目录执行：

```powershell
python scripts/run_queries.py
python scripts/validate_case.py --results outputs/raw/2026-08-05_2026-08-11
python scripts/summarize_results.py outputs/raw/2026-08-05_2026-08-11
```

只运行部分 SQL：

```powershell
python scripts/run_queries.py --queries 00,01,02,03,06
```

结果复制到 `outputs/raw/<开始日>_<结束日>/`。默认不执行包含玩家 ID 的 `04`；需要时显式传 `--queries 04`，并限制文件访问范围。
`summarize_results.py` 会生成 `analysis_summary.json`，其中包含单排对手结构、严格段位不均衡，以及按共同“日期×段位带”样本结构计算的标准化 Bot 率。

## 历史基线（2026-06-24 至 2026-07-20）

以下是旧项目已经取数并通过结构校验的快照，仅用于回归比较，不代表当前状态：

- 168 万排位对局；真人对真人对局占 22.79%。
- 真人局单排玩家对手：纯单排 84.67%、含双排 13.47%、三排 1.87%；对应胜率 50.02%、49.09%、42.11%。
- 严格段位不均衡对局率 14.96%；被严格压制方胜率 23.04%，平均段位差 4.62。
- Raw 玩家暴露 Bot 率：单排 42.83%、双排 33.26%、三排 20.35%。
- 日期×段位带标准化后：单排 40.86%、双排 34.94%、三排 24.81%。
- 双排总体 41,399 人；按旧阈值进入高优先级复核 3,517 人（8.5%）。这只是筛查漏斗，不是作弊人数。

## 已知限制

- `rank` 同时被用作胜负和阵营代理，必须持续用 00 号 SQL 验证每局恰有两个值。
- 段位来自结算事件，刚好升段的边界样本可能污染赛前段位；21 与 22+ 分开查看可减轻该问题。
- 有 `battle_id` 的 `match_cost` 只覆盖成功形成对局的匹配，未成功进入战斗的真实超时可能缺失。
- 组队次数的 `1/queue_size` 加权只是没有 `party_id` 时的估算，不能当作精确队列数。
- 任何策略变更验证都应至少保留变更前后窗口、每日趋势、样本量和缺失率。

## 交付前 QA

按 [VALIDATION_CHECKLIST.md](VALIDATION_CHECKLIST.md) 逐项检查。最重要的是：00 号覆盖率通过、01 三类占比和为 100%、02 不均衡子集不超过真人局、各比例位于 0–1、星耀规则按 21 与 22+ 分层、不同 Bot 分母不混用。
