# 方法与口径

## 1. 分析问题

目标是回答两组灌篮全球版新增账户，在约第 30 天观察窗口结束时，其已有角色的最新段位分布：

1. 2026-04-23 ~ 2026-04-26 新增，观察至 2026-05-26。
2. 2026-06-04 ~ 2026-06-07 新增，观察至 2026-07-07。

数据迁移导致两组 cohort 分别由阿里云和数数承载，因此两端独立查询后再统一字段、排序和占比计算。

## 2. 为什么不是“截止日当天活跃用户”

业务要求是“有快照就取整个周期最后一条”，因此不能把样本限制为 5 月 26 日或 7 月 7 日当天活跃角色。否则会把已经注册、有历史段位、但截止日当天未登录的角色排除，得到的是“D30 当日活跃角色段位”，而不是“新增 cohort 截至 D30 的最新段位”。

正确逻辑为：

```text
新增账户 cohort
    → 找到观察窗口内该账户的全部角色快照
    → 每个账户 + 角色按日期/事件时间倒序
    → 取最后一条有效段位快照
    → 按段位汇总角色数和占比
```

## 3. 账户与角色粒度

- 新增发生在账户粒度：阿里云 `lcm_id`，数数 `#account_id`。
- 段位发生在角色粒度：`role_id/user_id`。
- 合并键为账户 ID；汇总去重键为 `账户 ID + role_id`。
- 一个新增账户若建立多个角色，多个角色都会进入分布。这与“段位分布”的角色口径一致，但不能将结果解读为新增账户数。

## 4. 阿里云逻辑

### 4.1 新增账户

来源：`dm_platform.daily_lcx_user_info`。

- `app_id = 63002013`
- `reg_day BETWEEN 20260423 AND 20260426`
- 排除水号：`is_water = '不是水'`
- 为满足 MaxCompute 分区扫描要求，同时限制 `day BETWEEN 20260423 AND 20260526`

### 4.2 现场还原角色快照

历史中间表 `g63002013_dev.dm_server_user_info` 已停更，所以不能直接读取。查询内联还原原构表逻辑：

- `g63002013.daily_user_snapshot`：账户、角色、区服、登录时间、`match_rank`。
- `g63002013.daily_vip`：按账户、角色、日期聚合 VIP；当前结果不使用 VIP，但保留连接以忠实记录历史构表口径。
- `g63002013.dim_rankname`：把 `match_rank` 映射为段位名称。
- `FROM_UNIXTIME(last_login) >= 当日日期`：保留该日有登录的日快照。

随后按 `lcm_id + role_id`、`snapshot_day DESC` 取最后一条非空段位快照。

### 4.3 为什么不使用长度/区服过滤

历史繁中项目 SQL 曾使用 `LENGTH(lcm_id)=10` 和区服前缀 `1/2/3`。这些条件不适用于全球版 GL；套用后会错误清空或大幅缩小样本。因此本 case 不使用这两个过滤条件。

## 5. 数数逻辑

### 5.1 新增账户

来源：`ta.v_event_21`。

- `"$part_event" = 'NUU'`
- `"$part_date" BETWEEN '2026-06-04' AND '2026-06-07'`
- 账户键：`#account_id`

### 5.2 最新角色快照

- 扫描 `2026-06-04` 至 `2026-07-07`。
- 事件名匹配 `snapshot$`。
- 在排序前排除 `match_rank IS NULL`。
- 按 `mbga_uid + user_id` 分组，以 `$part_date DESC, #event_time DESC` 取最后一条。

### 5.3 数数段位阈值

| match_rank | 段位 |
|---:|---|
| `< 16` | 入部新秀 |
| `< 32` | 强力替补 |
| `< 52` | 最佳正选 |
| `< 72` | 绝对主力 |
| `< 96` | 超级明星 |
| `< 120` | 最强王牌 |
| `< 150` | 传奇巨星 |
| `< 170` | 殿堂王者 |
| `>= 170` | 灌篮高手 |

## 6. 跨平台合并

两份 SQL 输出相同字段：

| 字段 | 说明 |
|---|---|
| `data_source` | `ODPS` 或 `TA` |
| `cohort_window` | 新增日期范围 |
| `snapshot_day` | 观察截止日 |
| `rank_name` | 段位名称 |
| `role_count` | 去重角色数 |

Python 脚本纵向合并两端结果，再在各自 `data_source + cohort_window + snapshot_day` 内计算 `rank_share_pct`。两组 cohort 日期不同，不能直接把人数合计为一个总体段位分布。

## 7. 已知限制

- 本 case 的“D30”是固定业务观察日，不是每个注册日严格的 `date_add(reg_day, 30)`。
- 只统计观察窗口内至少出现一次有效段位快照的角色；完全没有段位快照的新增账户不进入分母。
- 结果是角色分布，不是账户分布。
- 阿里云与数数的新增识别字段不同，迁移重叠期若做同一 cohort 的跨源拼接，需额外进行账户去重和来源优先级设计；本 case 两组 cohort 分别由单一来源控制，不做跨源账户拼接。
- 维表段位名称和数数阈值需要随版本变更复核。
