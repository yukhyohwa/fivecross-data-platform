# Jump Assemble TC｜8/19 后付费率上升诊断

## 问题

验证 2026-08-19 后 Jump Assemble TC 的付费率是否显著上升，并判断新增小额礼包、既有「躍之星」SKU 与后续消耗去向各自的作用。

## 结论摘要

- 付费率上升成立：8/14–18 为 **3.84%**（2,001 / 52,087），8/19–23 为 **7.38%**（3,758 / 50,956），增加 **3.53pp**，付费人数增加 **1,757**。
- 这是活动期更多用户付费、同时 ARPPU 下降的变化；不能仅凭此判定为长期基线改善或因果效果。
- 新增小额礼包存在，但四个新增 SKU 的收入合计仅 **US$1.59k（2.39%）**，不是本次变化的主因。
- 既有「躍之星」档位的付费人数增长明显：
  - 躍之星 x340個（`nt170_340`）：85 → 619（+534）
  - 躍之星 x580個（`nt290_580`）：175 → 367（+192）
  - 躍之星 x1260個（`nt630_1260`）：182 → 223（+41）
- 对 8/19–23 仅购买 `nt170_340` 的 142 位用户，付费躍之星的两大消耗去向是：
  - 活动试炼 1008／「学园开放日测试数据」：37,415（33.4%）
  - 解锁进阶战令：37,387（33.4%）
- 「学园开放日测试数据」是商品维表名称，对应活动试炼商店 `shop_id=1008` 的两个 `goods_id`：`303802`（36,657）与 `303804`（758）。该名称在现有维表中是复用的泛名称，仍需配置表补充具体道具内容。

## 口径

- 对比窗口：前五日 **2026-08-14 至 2026-08-18**，后五日 **2026-08-19 至 2026-08-23**；日界为 Asia/Shanghai。
- 付费率 = 付费设备数 / 活跃设备数。SKU 对比中的付费人数限定为各窗口内有 `LOGIN_SUCCESS` 的用户。
- 排除：`internal_users`、`is_water`、`is_water_mod`、`suspicious_ip`；购买排除 `SANDBOX_RECEIPT`。
- `only-nt170_340` cohort：后五日内仅购买一个不同 SKU，且该 SKU 为 `nt170_340`；历史窗口外购买不纳入「only」判定。
- SKU／商品分类付费人数可重叠，不能横向加总为总付费人数。

## 可复用分析思路：付费率异常诊断

本 case 的目标不是只解释一次活动，而是形成一套每次付费率异常都可复用的诊断顺序。原则是：先验证指标变化，再找新增付费者来自哪里，最后才讨论具体商品或活动的归因。

### 1. 先确认问题是否成立

1. 选定异常日前后对称窗口；优先使用 5 日或 7 日，并固定业务日界与排除名单。
2. 同时输出活跃数、付费人数、付费率、收入、ARPPU：
   - `pay_rate = payers / active_users`
   - 付费率上升而活跃不变／下降，通常意味着转化提升；反之需要先排除流量结构变化。
   - 付费人数上升、ARPPU 下降，常见于低门槛付费者扩张；付费人数不变、ARPPU 上升，通常是高客单 SKU 或大额用户变化。
3. 对前后窗口的付费率做两比例检定，并把 p 值、样本量和百分点变化一起报告。统计显著只证明变化可靠，不证明活动或商品导致变化。

### 2. 将付费率拆成「人数」而不是只看收入

1. 用 `付费人数 = 活跃人数 × 付费率` 解释绝对增量，先回答增加了多少人。
2. 按商品分类、SKU、平台、付费历史档位、首付／复付用户拆分付费人数。
3. 所有 SKU／分类表都应标注「用户可跨行重复」，不要把各行人数直接相加为总付费人数。
4. 对核心 SKU 使用同口径的前后窗口并列图；重点看 `post_payers - pre_payers`，而不是只看后期收入排名。

### 3. 判定新增商品是否是主因

1. 先根据商品目录确认 SKU 的名称、价格、内容、上架时间和是否首上；不能仅凭 SKU ID 断言为新品或小额包。
2. 对疑似新增 SKU 同时看：付费人数、收入、首次付费人数、其用户与总体新增付费者的重叠关系。
3. 若新增 SKU 收入／人数较小，或大多数新增付费者购买的是既有 SKU，则将其定位为辅助因素，而非主因。
4. 需要严谨归因时，构造互斥用户分组：仅买新增 SKU、仅买既有 SKU、两者都买；再比较各组的首次付费和活动参与路径。

### 4. 追踪虚拟货币消耗，连接「买什么」与「为什么买」

1. 对目标 cohort（例如仅购买某个 SKU 的用户）计算付费货币消耗；cohort 定义必须写清时间范围和「only」是否限制历史购买。
2. 先按一级消耗动作拆分，例如商城购买、战令进阶、道具兑换、运营活动奖励。
3. 对占比最大的一级动作继续下钻到 `shop_id + goods_id + goods_name`；若维表名称复用或缺失，保留原始 ID 并标记待补配置。
4. 核对购买事件与货币扣减事件的时间、用户和资源 ID，避免把免费货币或无关资源变动误归因。

### 5. 写结论时区分「观察」与「因果」

| 层次 | 可以给出的结论 | 不能直接给出的结论 |
| --- | --- | --- |
| 指标验证 | 付费率在活动同期显著上升 | 活动一定导致上升 |
| SKU 对比 | 哪些 SKU 的付费人数增加最多 | 某个 SKU 独自带来全部新增用户 |
| 货币消耗 | 购买后主要消耗在哪些动作／商品 | 消耗动作是购买的唯一动机 |
| 业务判断 | 活动期转化提升、需持续观察 | 长期付费率已结构性改善 |

### 6. 建议的标准产出

1. 一页总览：前后窗口的活跃、付费人数、付费率、收入、ARPPU。
2. 一页趋势：按日付费率，并标出异常／活动开始日。
3. 一页 SKU 人数对比：核心 SKU 的前后付费人数、商品中文名称及新增人数。
4. 一页目标 cohort 消耗：一级动作与占比，并下钻最大动作的商品／道具 ID。
5. 一页结论与下一步：商品目录补全、互斥归因、活动结束后 7 日观察。

## 限制与后续

- 当前证据支持「与 8/19 活动期同步的转化提升」，不支持单一 SKU 或活动对付费率变化的因果归因。
- 商品维表存在未映射商品 ID 与复用名称；下一步应接入商品配置表（价格、内容、上架时间、首上标记）。
- 建议继续观察活动后 7 天的付费率、ARPPU 与首次付费者留存，以判断是否回落至活动前水平。
