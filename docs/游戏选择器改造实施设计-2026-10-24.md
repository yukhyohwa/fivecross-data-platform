# 游戏选择器改造 · 实施设计（2026-10-24，评审修复版 2026-10-25）

> 用户已拍板（2026-10-24）：
> 1. 顶部导航选择器保留、聊天窗口的也保留不动；聊天侧栏新增二选一：① 不选游戏 ② 自动抓取右上角选择的游戏（永远与右上角一致，右上角切换侧栏同步）。
> 2. 「不选游戏」提问：选项 = 全部有权限游戏，**多选**；多游戏按顺序执行查询并拼接结果；专项报告 = SQL 分开查、结果拼起来、报告用拼后数据。
> 3. 零权限用户：告知无权限，**不能查任何数据**（不回落）。
> 4. （既有，已实现）点名别的游戏走鉴权：通过就查、不通过追加提示。

> 本版已并入设计评审对抗审查（2026-10-25，4 路批评者 29 条 findings，去重 26 条）全部修复，见 §七。

## 一、总体方案

**哨兵头**：聊天页「不选游戏」模式下，对 `/api/chat*` 与 `/api/agent/chat/stream` 请求下发 `X-Game: __any__`。
`deps.get_game` 识别哨兵 → 仅对聊天端点返回 `None`（RBAC 零权限仍 403；**非聊天端点把哨兵当缺省 key 回落允许集第一项**，防 ~40 个 `Depends(get_game)` 消费者 500，评审修复 5.5）。
`chat.py` / `agent.py` 拿到 `game=None` 后走「哨兵绑定」：点名 → 目标游戏；多选卡回传 → 绑定多游戏；会话记忆 → 延续上一轮选择；唯一有权限游戏 → 自动绑；
否则 → 发 **多选卡**（`game_select` 事件）提问。

**多游戏执行 = 复用既有机制**：`_execute_steps` 多库分支（逐库 apply_sql → 插「地区」列 → concat）与
`build_data_block(query_results)` 报告层已支持多地区合并——「SQL 分开查、结果拼、报告用拼后数据」是接线而非新机制。
深度分析 `query_database` 照抄该模式（**门控 = `len(ctx["games"]) > 1`**，单游戏绑定不插伪「地区」列，评审修复 1.2）。

**零权限**：`deps.get_game` 允许集为空 → 403（文案改为明确「无任何游戏权限，无法查询数据」）；前端选择器/聊天页显式提示。

  其余端点（meta/knowledge、schema、skills、sql_admin、models、kb_admin、indicators、reports、sql_history、chat_history）继续拿右上角真实游戏，**不改**；伪造哨兵打到它们时按缺省 key 回落，不 500。

### 2. `backend/routers/chat.py`

**(a) ChatRequest 新增字段**：
- `target_games: list[str] | None` — 多选卡回传（一次性，优先级最高）。
- `session_games: list[str] | None` — 会话延续（追问/refine 时前端携带，优先级最低，后端按权限过滤）。
- SuggestReq/SuggestMergeReq 增 `games: list[str] | None`（mode=none 时前端传 sessionGames，供游戏恢复）。

**(b) 新增 `_sentinel_bind(question, req, engine, user, preset_skill=None, ai_target=None)`** → `("run", query_games, game, game_key, note, direct)` 或 `("ask", games_options, preselected, reason)`：

优先级：
1. `req.target_games`（多选卡回传）→ **先按 games.get_games(engine) 的 key 集校验再 resolve**（未知 key 直接丢弃——`resolve()` 对未知 key 静默回落默认游戏，会绕过越权过滤，评审修复 3.3）→ `is_game_allowed` 过滤 → 去重 → 全部无效则 ask；
2. 问题点名（`match_game_in_text`）：
   - 有权：家族主键 → 展开家族（成员逐个 `is_game_allowed` 过滤，评审修复 3.4）→ 多地区时 **ask 卡预选家族成员**（与既有「点名=当前选中家族主键 → 确认卡」对称）；具体地区服 → 直接 run（direct）；
   - 无权 → **ask 卡**（reason=无权限提示，选项=有权限游戏）；
3. `req.session_games`（先 key 集校验 + 权限过滤，非空）→ run；
4. `preset_skill` 的 `read_skill_meta(skill).game` 绑定游戏（有权）→ run；绑定游戏无权/不存在 → ask；
5. 有权限游戏恰 1 个 → 自动 run（附说明）；否则 → ask（全部有权限游戏，无预选）。

**(c) `_handle` 接线**（`game=None` 时；评审修复 0.1/0.2/0.3/0.5/0.8/0.9 全覆盖）：
- 入口（2046-2048）：`game_key = game["key"] if game else None`；`selected_game = game`；`query_games = [game] if game else []`。
- **绑定辅助**（generator 内 `yield from`）：`bound = yield from _sentinel_ensure(question, req, engine, user, preset_skill=skill, ai_target=...)` →
  返回 None 表示已发 `game_select` 卡 + `stage(match, "待选择分析游戏…")`，调用方直接 return；
  否则 `(query_games, game, game_key, gm, direct)`。**绑定 run 时同步 `selected_game = game`**（否则 2401 `selected_game["key"]` TypeError）。
- 绑定点（全部 `game is None` 才走，game 非 None 走原 `_resolve_game` 路径零改动）：
  - **preset 分支**：问候/`_needs_rewrite` 闲聊应答之后、`_resolve_game` 之前（`preset_skill=skill`）。`ks.list_skills(game_key)` 校验在绑定后执行（game_key 已具体）。
  - **auto 首轮**：
    - explicit_skill / rerun_skill（2124-2150）：命中专项后绑定（`preset_skill=命中技能`）；rerun 无上下文反问在绑定前 return。
    - Joydata 分支不改（`_joydata_pick_project` 已 `(game or {})` 容忍 None）。
    - decide 之后：
      - intent ∈ chat / clarify：绑定前 return（无需游戏）；
      - **intent ∈ knowledge / model / modify / generate**：各自分支入口先绑定（knowledge 不绑定会把 game_key=None 透传给 answer_knowledge，`visible_to` 隔离被整体跳过、跨游戏跨用户作答，评审修复 0.5）；
      - intent == query：route_deep 在绑定前 return（深度流自己做绑定）；否则绑定后继续。
- **确认链 re-POST 分支**（candidate 2503 / rewrite 2564 / ai_report 2589 / forecast 2613 / generate 2631 / game_confirm 2642 的 ok 与 "" 两分支 / confirm="" 2666 / confirm=技能名 2673）：`game is None` 时全部改走 `_sentinel_ensure`（`ai_target=req.target_game`），不再裸调 `_resolve_game`（评审修复 0.2/0.8）。game_confirm=="" 且 selected_game 为 None（陈旧回传兜底）→ 同样走哨兵绑定。
- **多选卡事件**：`_event("game_select", question=…, games=[{key, name, label=region_label(g)}…], preselected=[…], reason=…)` + `stage(match, "待选择分析游戏…")` + return（**game dict 无 label 字段，label 一律服务端 `games.region_label(g)` 现算**，评审修复 1.5）。
- game_confirm 卡发出条件（2401）：`selected_game is None` 时不发（哨兵模式无「当前选中」概念）；绑定后 selected_game 已重绑，2401 的比较语义不变。
- **专项存在性校验（2116/2677）**：`len(query_games) > 1` 时改为对 query_games 各 key 的 `list_skills` 并集校验，不再只按主游戏——绑在次选游戏上的专项不被误报「不存在」（评审修复 0.7）。检索/专项匹配仍按主游戏 key 作用域（文档化降级语义：检索看主游戏、次选只参与 SQL 执行）。

- 其余（检索/专项匹配/执行/报告）**零改动**——query_games 多元素即触发既有多库执行与拼后报告。

**(d) 附属端点 `game=None` 容错**（评审修复 0.4 路由层解引用 + 3.1 export-csv 越权口）：
- `export-csv`：ExportCsvReq 增 `db: str | None` 与 `sqls: list[dict] | None`（`[{sql, db, label}]`）。

  - `chat/suggest-merge`：build_merge(kind="sql") 需要真实 db → game=None 时按 body.games[0]（先校验再 resolve）取 db；无 games → 400「未指定游戏，无法生成合并草稿」。
  - `chat/gaps`：game 不参与取数（读 skill meta + gap 分析）→ 路由层不传 game 字段即可。
  - `chat/gap-fix` / `gap-fix/apply` / `gap-answer` / `gap-answer/apply`：恢复链：`read_skill_meta(skill)["game"]`（专项绑定游戏）→ resolve → key/db；专项无绑定游戏 → 400「专项未绑定游戏，请先在聊天窗口选中游戏」。kb 路径同样先恢复（统一口径）。

### 3. 深度分析链路（agent.py / agent_deep.py / agent_tools.py）

  - run → `ctx["game"] = 主游戏`（games[0]），`ctx["games"] = [g…]`（单游戏时列表长度 1）。

**(c) `agent_deep.run_agent_stream`**：

- `_preload_assets` / `search_knowledge` / `list_special_skills` / `search_indicators` / 三个 schema 探查工具：仍用主游戏（ctx["game"]），system prompt 已明示（评审修复 1.4）。
- caveat 来源（647）：多游戏时列出全部库。

**(d) `agent_tools.query_database`**：门控 `games = ctx.get("games") or []`，**`len(games) > 1` 才走多库分支**（评审修复 1.2）：逐库 `apply_sql` → `run_raw_sql` → 单库失败跳过 → 插「地区」列（原「地区」改名「地区(原)」）→ concat；返回 `{"sql": <主库 applied SQL>, "games": [{key, db}…], "result": preview}`；信封模式 `store.put(sql=主库 SQL)`，**且 `result` dict 内附 `"games": [{key, db}…]`**（tool_result_to_str 只序列化 result["result"]，顶层字段模型看不到，评审修复 1.7）。全部库失败 → 照单库报错路径。

## 四、边界与安全

| 场景 | 行为 |
|---|---|
| 零权限 + 哨兵/正常 | 403 明确文案；前端选择器禁用 + 聊天页横幅禁输入 |

| 多游戏专项存在性 | 并集校验（不误报「不存在」）；检索/专项匹配按主游戏作用域（文档化） |
