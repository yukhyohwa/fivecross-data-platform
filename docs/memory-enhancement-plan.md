# 记忆管理增强方案（参谋稿 · 待确认）

> 2026-10-21 拟稿。对应用户三个设想：① 记忆按对话类型打标（日常/专项/SQL/知识库/算法）并绑定资产；② 聊天窗口加「启用记忆」开关；③ 新记忆放「用户应用-个人定制」下。
> 文末【待确认点】是需要用户回来拍板的 5 项，其余均可自动实施。

---

## 一、现状诊断：为什么记忆现在「没啥用」

先盘点现状（已核实代码）：

| 环节 | 现状 |
|---|---|
| 存储 | `agent_memory` 表（ide_data.db）：user_id / scope（private/global）/ category / key / content / source / hit_count |
| API | `/api/memory` 全套 CRUD + 检索 + 分享 + 导入导出 + 术语表迁移（P4 融合时已是一等公民接口） |
| 管理页 | 「AI配置 → 记忆管理」（React MemoryPage），支持搜索/编辑/删除/分享/导入导出 |
| 写入 | **只有深度分析 Agent 显式调用 `save_memory` 才会写**。`auto_extract`（对话自动提取）函数存在但**全库无任何调用点，从未接线** |
| 注入 | 仅深度分析启动时 `build_memory_context`：**用户私有记忆全量 20 条无差别注入** + 全局记忆按关键词 10 条 |
| 普通聊天 | 完全不注入、不写记忆 |

三个关键缺陷，解释了「记了也没用」的体感：

1. **自动沉淀从未生效**——原本设想的「聊完天自动提取记忆」一直没接线，当前只靠 Agent 自己想起来调 save_memory。
2. **注入无差别、噪声大**——聊「流水达成」时把「充值口径」「投放」「术语」等全部私有记忆不分话题塞进提示词（上限 20 条），既不精准也没重点。
3. **只深度分析用**——普通聊天链路零记忆参与。

## 二、方案设计（三块）

### 2.1 记忆按类型打标 + 绑定资产（专项/SQL/知识库/算法）

- `agent_memory` 加两列：`mem_type`（`日常|专项|SQL|知识库|算法`，默认 `日常`）、`bind_name`（绑定资产名；`日常` 恒为空）。旧数据默认 `日常` 无损。
- `save_memory` 工具加可选参数 `mem_type` / `bind_name`；深度分析提示词增加打标规则：**本轮命中了某资产（read_special_skill / read_sql / read_kb_doc / read_indicator 等）时，沉淀记忆自动打对应类型并绑定资产名；未命中任何资产 → 标记「日常」、不绑定**（与用户设想一致）。
- 检索升级（核心价值）：`build_memory_context` 从「全量注入」改为「**按需召回**」——用当前问题匹配 `bind_name` + 内容关键词，只注入相关记忆；每条注入的记忆附带「来源资产」线索，Agent 据此调 `read_special_skill('流水达成分析')` 把专项 md 一并读入，形成「**个人记忆 + 专项方法说明**」双层上下文（正是用户说的「结合专项和个人记忆执行」）。
- 记忆管理页加「类型 + 绑定资产」徽标与筛选。

### 2.2 聊天窗口「启用记忆」开关

- chat.html 深度分析开关旁加同款式「💾 启用记忆」开关。
- **开关状态建议存后端用户级**（而不是 localStorage）：深度分析在后端跑，后端必须可靠知道状态；localStorage 换浏览器/清缓存即丢。前端开关只是遥控。
- 关闭时：深度分析不注入记忆上下文，且提示词禁用 `save_memory`/`search_memory`（不写也不读）；打开恢复。
- 我的参谋意见：**建议做，默认开启**。用户要的是「灵活丰富地提供分析能力」，记忆开关是逃生门（隐私/降噪场景一键关），符合「人治」原则。

### 2.3 记忆管理挪「用户应用 → 个人定制」

- 个人定制 PersonalWorkspace 现有 5 个 tab（订阅报告/个人SQL/个人专项/个人知识库/聊天记录），加第 6 个「个人记忆」直接挂 MemoryPage（React 组件复用，无 iframe，常驻保活同现有模式）。
- 「AI配置 → 记忆管理」入口建议删除，个人定制为唯一入口（避免两处入口不一致）。
- 与现有「个人知识库（习惯记忆）」的区分：知识库 = 给 AI 的背景文档（.md，走知识库检索）；新记忆 = 对话沉淀的口径/偏好/习惯（agent_memory 表，带类型+绑定）。两个入口并列、语义互补。

## 三、实施顺序（可自动做的部分）

| 优先级 | 内容 | 是否可自动 |

## 四、待确认点（回来拍板即可，共 5 项）

1. **记忆开关的作用范围**：只影响深度分析，还是普通聊天也注入记忆？
   现状普通聊天零记忆注入。建议先只做深度分析（改动小、语义清晰）；普通聊天若要注入，工作量大一圈。
2. **开关状态存哪**：建议后端用户级（跨端一致、后端可靠读取）；localStorage 方案更简单但换浏览器即丢。
3. **自动提取（auto_extract）是否这次一并接线**：建议接线，受开关控制、异步不打扰——补上「对话自动沉淀」闭环，否则记忆库只能靠 Agent 显式保存、增长缓慢。
4. **AI配置下的「记忆管理」入口**：建议删除，个人定制为唯一入口。
5. **手动新建记忆是否也支持选类型/绑定**：建议支持（新建弹窗加类型下拉 + 资产下拉，可留空=日常）。

## 五、不做的事（边界）

- 不动普通聊天链路（除非确认点 1 拍板要做）。
- 不改 `agent_memory` 现有字段语义（scope/category 保留，category 继续当细分类用，类型是新增正交维度）。
- 记忆不分层级（个人私有为主；global 系统公用维持现状，分享机制已存在）。
- 不引入新的向量库/嵌入检索——SQLite LIKE 关键词匹配 + bind_name 精确匹配已够用，保持零依赖。
