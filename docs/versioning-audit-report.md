# 版本库审计报告（2026-10-21 · 对抗审查工作流产出）

> 回答用户问题「目前是否有版本库？大概会保存多久的版本变化？防止误操作导致的版本覆盖/历史遗失/误删除，还有什么好的建议？」
> 方法：四路扫描 36 条候选发现 → 逐条读代码对抗验证 → CONFIRMED 33 / PARTIAL 3 / REFUTED 0，另补漏 6 条系统性缺口。

---

## 一、版本库现状（直接回答）

**有版本库**：`streamlit/private/game_analytics/_versions/`（按源文件相对路径镜像，当前 450 个版本文件 / 2.8MB，最老 2026-09-24 仍在）。

| 覆盖对象 | 机制 | 保留时长 |
|---|---|---|
| SQL / 知识库文档 / 专项包（skill.md、meta.json、内嵌 sql·models·knowledge 快照）/ 算法代码 / 术语表 / 笔记 | 每次**覆盖写**前自动 snapshot（`versioning.write_text`：先备份再原子替换，内容指纹去重） | **7 天**（`RETENTION_DAYS=7`），且是**惰性清理**：只在同一文件再次产生新版本时触发，无后台定时任务 |
| 已删除的文件 | 其 `_versions` 镜像目录**不会被清理**（无人再写它），成孤儿长期留盘 | 实际可能超过 7 天（10-21 事故能恢复正是靠这个） |
| 数据库（ide_data.db） | 启动时 SQLite backup API 快照，保留最近 10 份、6 小时限频 | 按当前节奏约 10 天 |
| 前端 dist / 聊天记录 / 订阅 / run.json / provenance.json / 文档元数据 | **无任何备份或版本化** | — |

**回滚入口**：`/api/admin/versions`（list/diff/restore）已存在，restore 前自动备份当前（回滚可反悔），非管理员的「数据分析」角色可自助使用；前端四个工作台的版本历史弹窗可查看/对比/回滚。

## 二、审计结论：真正的缺口全在「删除侧」

写路径几乎全覆盖版本化（这是好消息），**所有 delete 类函数都是裸 unlink/rmtree，删除前无 snapshot、无墓碑**。逐条验证确认的缺口（按风险排序）：

### 高风险（正是本次事故的机制）
1. **`_prune_dir` 裸 unlink**（knowledge_store.py:305）：自动关联/快照整体替换绑定后，`write_skill_bundle` 末尾剪掉解绑孤儿快照，**删除不版本化**——10-21「投放效果分析 9 个内嵌 SQL 快照被刷掉」正是此路径。已修「只剪真孤儿」，但删除本身仍无备份。
2. **`_delete_bundle` 整目录 rmtree**（knowledge_store.py:243）：删专项时 run.json/provenance.json 一并销毁，这两类文件**全程从未进版本库**（atomic_write_text 裸写），删除后不可恢复；且删除后 versions API 的 skill 路径解析回退到扁平路径，**历史版本 API 层彻底不可见**，只能人工拷 `_versions` 文件。
3. **全库无 VCS 兜底**：chat_bi / streamlit 主应用 / tools 均非 git 仓库（仅 sql-ide 只读参考 + joytools 子树有 .git）。代码被误改误删无法用 git 找回；`_versions` 本身是历史唯一单副本，**整目录误删/磁盘损坏则历史一次性归零**（写路径会自动重建空目录，无声无息）。

### 中风险
4. **SQL 删除不版本化**（sql_store.py:151）：`.sql` 与 `.sql.json` 裸 unlink，两个入口（后端删除路由 + streamlit SQL 编辑器）都无备份、无确认；已删文件的版本目录成孤儿，前端无回收站入口，恢复靠人工记得文件名。
5. **算法删除不版本化**（code_store.py:61）：`.py`/`.py.json`/专属冻结 `.sql` 三件裸 unlink；且 `delete_model_sql`（:97）被 **save/refresh 静默触发**——模型改造件为空/被移除时，点保存就删掉旧冻结件，无确认、无 pre-delete snapshot，且版本历史弹窗从不列出 `.sql` 版本（无 UI 可回滚）。
6. **文档删除不版本化**（knowledge_store.py:51）：`.md` + 元数据 `.json` 裸 unlink；streamlit 知识库页删除按钮连确认弹窗都没有。
7. **单件快照删除不版本化**（knowledge_store.py:605）：`/snapshot/delete` 裸 unlink；前端弹窗只说「回退全局源」，不披露「本地改编过的冻结件被删即永久丢失」。
8. **改名丢历史**：文档/模型改名是前端两段式「先存新名再删旧名」，旧名 `_versions` 历史成孤儿不随迁（专项改名已实现原子迁移，docs/models 还在用旧模式）。
9. **聊天记录删除/过期清理无备份**（chat_history.py:160）：7 天留存期 + 手动删除都删唯一副本。
10. **RETENTION_DAYS=7 太短**：误操作超过 7 天才发现、且该文件期间又被写过 → 事故前版本被惰性 prune 静默清掉，彻底无法找回。

### 低风险（顺手可修）
11. `table_schema.json` 裸写（非原子、无版本）；12. dist 无历史归档（只能从 src 重建，服务器无 Node）；13. 备份无定时任务（DB 快照只靠重启触发，长期不重启无新快照）；14. `_snapshots/chatbi_report_20261009` 是一次性归档，此后从未刷新；15. prune 只有单文件惰性形态，无全库巡检/体积告警。

### 补漏发现的系统性缺口（清单之外）
- **并发写冲突无检测**：chat_bi 后端与 streamlit webapp 双进程写同一内容根，两人同时编辑同一文件后写静默覆盖，无冲突提示。
- **操作级审计日志整体缺失**：谁/何时/改了什么无记录，批量误操作无法定位责任人与时间范围。
- **ide_data.db 行级误操作无撤销**：删用户级联清掉其全部记录，恢复只能整库回退 10 份快照之一。
- **encryption.key 单点**：被误删后静默生成新 key，旧密文永久失读。
- **无「钉版」机制**：重要基线无法豁免 7 天滚动清理，批量危险操作前无法一键建恢复点。
- **write_skill_bundle 多文件写无事务性**：中途中断留下包内新旧混杂。

## 三、改进建议（按性价比排序，均待确认后实施）

| # | 建议 | 代价 | 收益 |
|---|---|---|---|
| 1 | **给 versioning 加删除 API**（`delete_text(target)`：先 snapshot 再 unlink），所有 store 的 unlink/rmtree 换成它 | 小（一个函数 + 约 8 处调用点替换） | 直击本次事故：删除可回滚，删错能找回 |
| 2 | **RETENTION_DAYS 7→30 天**（或按工件分级：SQL/专项/模型 30 天） | 一行改动，版本文件很小（现共 2.8MB） | 误操作 7 天宽限期太短的问题 |
| 3 | **run.json / provenance.json / 文档元数据改走 versioning.write_text** | 小（约 6 处替换） | 补上版本库盲区 |
| 4 | **game_analytics（或至少 chat_bi+game_analytics）git init** | 一次性，无运行代价 | 代码层 VCS 兜底，最高性价比的长期保障 |
| 5 | **_versions 每日异地备份**（Windows 计划任务 robocopy 到另一目录/盘） | 一个计划任务 | 防整库误删/磁盘损坏 |
| 6 | **删除确认弹窗统一补文案**：「删除后仅可从版本库恢复，保留 N 天」 | 改 4 个弹窗文案 | 用户删除前知情 |
| 7 | 文档/模型改名改为后端原子 rename（对齐专项已有实现，含 _versions 迁移） | 中 | 改名不断历史链 |
| 8 | versions API 加「按镜像目录列出已删工件」端点 + 前端回收站 UI | 中 | 已删文件自助恢复，不再靠人工拷文件 |
| 9 | 前端删除类按钮（SQL/文档/模型/专项）补确认弹窗 + 展示可恢复版本数 | 小 | streamlit 侧部分入口目前连确认都没有 |
| 10 | chat_history 删除改软删（rename 到 trash）；DB 备份加每日计划任务（不依赖服务重启） | 小 | 用户数据可恢复 |

**待确认项**：① 建议 1-3、6-10 是否实施（改动在 streamlit/game_analytics + backend，均属可自动做）；② 建议 4/5 涉及建 git 仓库与 Windows 计划任务，需要用户点头；③ 保留期天数（7→30？还是分级？）。

## 四、已存在的防护（正面清单，审计确认有效）

① 所有覆盖写路径版本化；② restore 回滚前先备份当前；③ 专项改名原子迁移版本目录；④ 路径穿越防护 + diff 512KB 截断；⑤ 前端四工作台删除均有二次确认弹窗（streamlit 侧除外）；⑥ 自动关联只增不减、三动作确认弹窗、_prune_dir 只清孤儿（本次事故后的三项过程防护）；⑦ ide_data.db 启动快照 + encryption.key 轮换备份；⑧ dist 漂移启动告警。
